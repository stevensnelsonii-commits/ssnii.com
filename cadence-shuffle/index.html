The class shuffle, run ten times.

Cadence is the scheduling program we're building for Warren County Summer Music School. This video runs the scheduler ten times in a row on last year's practice data — and gets the same answer every time.

The Cadence scheduler running ten times on the anonymized practice data: 99 students, 35 classes, 693 requests.

How the shuffle works

Applications are processed first come, first served, in the order they came in. Each student's choices are tried in the order they ranked them. If a first choice is full, or it clashes with something already on that student's schedule, Cadence writes down why and moves on to the next choice automatically.

Anyone it genuinely can't place lands on a short list with the reason, and the open classes that would actually fit them. Nothing ever fails silently.

What happened in the video

Ten runs, one identical result. The data is last year's run-through, anonymized — real numbers, made-up names. Every name you see on screen is a practice name; no real student information has ever been in this system.

The honest part

46 of the 99 students end up one class short — and that's not the engine failing. 20 of the 35 classes were asked for more times than they have seats: Music Video alone had 57 asks for 16 seats. When demand runs past the chairs, somebody lands a class short no matter who does the scheduling. What Cadence does is show its work: each of those students is listed with the reason, and the open classes that fit them, so the list can be worked through by hand.

For Jen — how the student data is protected

This section describes the production release candidate — the RC1 build with its encryption layer, prepared on our release branch. It is not the live public demo linked above; that demo still runs without these protections, which is exactly why real student data has never been loaded into it. The note is written for the district IT review, limits included.

In one sentence: student records that Cadence saves on a device, and student-data files that travel between people, are now encrypted with a passphrase — they are no longer sitting in the browser as readable text.

What is encrypted

  • Saved scenarios on the device. A saved scenario contains the complete student list (names, grades, guardians, contacts, medical notes) plus every class request. These were previously stored in the browser's local storage as plain, readable text. They are now stored only as ciphertext.
  • The override audit trail — the log of manual placement changes, which names students — is encrypted the same way.
  • Files that leave the machine. A scenario file exported from Cadence is produced only in encrypted form, under a passphrase the sender sets for that file. A data file (for example a Rediker export) can likewise be sealed into an encrypted file before it goes into a shared folder or an email, and Cadence's Upload buttons recognize the sealed file and ask for its passphrase instead of failing.

Working data typed into the scheduler during a live session is not encrypted while it is on screen — the program has to show it to the person using it. The encryption covers what is saved and what is sent.

How it works

  • Cipher: AES-256-GCM — the standard authenticated encryption built into every modern browser (WebCrypto); no third-party cryptography code was added, and Cadence still makes no network calls.
  • Key derivation: the encryption key is derived from a passphrase with PBKDF2-HMAC-SHA-256 at 600,000 iterations (the current OWASP recommendation for this method), with a random salt per device — guessing passphrases is deliberately expensive.
  • Integrity: GCM authentication means a wrong passphrase and a tampered-with file fail identically and are refused; there is no partial or silent decryption.
  • Key handling: the derived key exists only in the tab's memory. It is never written to disk, never logged, and never put in a file. Locking the data (one click in the Scheduler) or closing/reloading the page destroys it. Exported files carry only the salt and iteration count needed to re-derive the key — never the key or the passphrase.
  • Passphrase: in the gated build, the entry password the team already uses doubles as the data passphrase — one password to sign in and unlock the data. Scenario files use a separate passphrase chosen per export, so a file can be shared without sharing the device password.

What this protects against

  • Shared school computers. Another person opening the same browser later cannot read saved student records out of the browser's storage — without the passphrase, the storage holds ciphertext. (This was the audit's main finding, and it is fixed.)
  • Casual access to a device or its files. The browser profile folder no longer contains a readable student list.
  • Files in transit. A scenario file or student-data export that lands in the wrong inbox or the wrong shared folder is ciphertext. It opens only with its passphrase, which should travel separately (a phone call, not the same email thread).
  • Quiet alteration. A modified encrypted file fails its integrity check on open and is refused, rather than importing altered records.

The honest limits

  • A passphrase is not an account system. Anyone who knows the passphrase and can open the app can read the data — that is what a passphrase means. There are no per-user identities, no per-user permissions, and no record of who unlocked the data. Real accounts remain the production step, and the decision about where student records live in production (district-hosted, managed service, or an agreed local procedure) is still WCSMS's to make. This layer hardens the interim local model; it does not replace that decision.
  • Out of scope, plainly: a determined attacker who has both the passphrase and the machine; malware already running on the computer; someone watching the screen during an unlocked session. Client-side encryption on a single shared passphrase does not defend against those, and this note does not claim it does.
  • No recovery. If the data passphrase for a device is forgotten, the encrypted saves on that device are unreadable — by design; there is no back door and no reset. Exported scenario files (with their own passphrases) are the practical backup.
  • Still one device, still no backup. The data home is unchanged: this browser, this machine. If the browser profile is deleted or "cleaned," the encrypted saves go with it. Encryption protects confidentiality, not durability.
  • Printed and exported working documents are unchanged. Rosters, contact lists, and medical lists are still produced as readable documents and printouts, because staff need them on paper. How those are handled is a school procedure question, not something this layer governs.
  • Old saves migrate forward. Scenario saves made before this change are plaintext on disk until the next time they are opened and re-saved with the data unlocked, at which point they are rewritten encrypted automatically. On a machine that has run the older build, treat the old plaintext as present until that migration has happened once.

What a reviewer can check

  • The encryption code is two small files: src/lib/crypto.js (the envelope format — self-describing JSON: cipher, KDF, iterations, salt, IV) and the vault section of src/lib/storage.js (key handling). The scheduling engine (src/lib/conductor.js) is untouched by this change, byte for byte.
  • Automated tests cover: ciphertext-only storage (no student name appears anywhere in a stored record), wrong-passphrase and tamper refusal, key drop on lock, legacy plaintext import, and encrypted file round-trips. Full suite: 56 tests passing, including the 44 pre-existing engine/export tests, and the verified scheduling baseline is unchanged (436 assignments on the October run-through data, identical result hash).
  • Cadence still makes no network calls; nothing about this change phones home or syncs anywhere.
